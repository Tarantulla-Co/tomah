# Data model — notes for the storefront developer

The authoritative definition is [`packages/db/prisma/schema.prisma`](../packages/db/prisma/schema.prisma).
This document explains intent and the rules the admin app assumes both apps follow.

## Ownership & coordination

- One PostgreSQL database, one Prisma schema, two apps.
- **Migrations are shared.** Coordinate before running `prisma migrate dev`.
  Prefer additive changes; never rename/drop a column the other app reads
  without a deprecation step.
- Both apps may read and write, but by convention:
  - Storefront **writes**: `Customer`, `Address`, `Order` + `OrderItem`
    (checkout), `Quote` + `QuoteLineItem` (quote request), `WholesaleAccount`
    (application intake).
  - Admin **writes**: everything, plus it owns all status transitions,
    pricing, approvals, fulfilment, invoices, and content.
- In practice the storefront does not write directly — it calls the admin
  API's **public surface** (`/api/v1/public/*`, see `docs/API.md`), which
  performs those writes with the invariants enforced (stock re-check, tax /
  shipping from settings, minted document numbers, pricing-visibility filter).

## Order lifecycle & `PENDING_PAYMENT`

Storefront checkout (`POST /api/v1/public/checkout`) writes the `Order` as
`PENDING_PAYMENT` before payment is captured. The Stripe webhook — or, in
dev with `PAYMENT_PROVIDER=manual`, `POST /api/v1/public/checkout/:ref/confirm-dev` — flips it to `PAID`,
which is where the admin fulfilment lifecycle begins.

The admin dashboard treats `PENDING_PAYMENT` as "not a real sale": it is
excluded from the order queue, `statusCounts`, reports, revenue, and customer
order history. Abandoned `PENDING_PAYMENT` orders currently just linger (no
sweeper yet).

## Money

- All amounts are `Decimal(12,2)` in the row's `currency` (ISO 4217, default
  `USD`). Do arithmetic with a decimal library, not JS floats.

## Pricing visibility — important

`Product.retailPrice` (and `ProductVariant.retailPrice`) are **public**.

`wholesalePrice`, `minimumOrderQuantity`, `isWholesaleAvailable` must **only**
be exposed to a customer whose `Customer.wholesaleAccount.status === "APPROVED"`.
Anonymous and non-approved requests must never receive these fields — filter
them out at the serializer, not just the UI.

## Stock

`Product.stockQuantity` is a single integer with provenance:

| Field              | Meaning                                                        |
| ------------------ | ------------------------------------------------------------- |
| `stockSource`      | `MANUAL` (staff edit) or `ACCOUNTING_SYNC` (Phase 8 sync job) |
| `stockSyncEnabled` | if `false`, the sync job must skip the row (manual override)  |
| `stockUpdatedAt`   | timestamp of the last stock write                             |

The storefront should treat `stockQuantity` as advisory for display and
re-check at checkout.

## Entity map

```
User ──< RefreshToken
User ──< AuditLog (actor)

Customer ──< Address
Customer ──1 WholesaleAccount ──? User (reviewedBy)
Customer ──< Order ──< OrderItem >── Product / ProductVariant
Customer ──< Quote ──< QuoteLineItem >── Product / ProductVariant
Quote ──1 Invoice ──< InvoiceLineItem
Customer ──< Invoice

Product ──< ProductVariant
Product ──< ProductImage
```

## Line-item snapshots

`OrderItem` (and, once priced, `QuoteLineItem` / `InvoiceLineItem`) copy the
`sku`, `name`, and `unitPrice` at the time of the transaction so historical
documents stay correct when the catalogue changes. `productId` / `variantId`
are nullable FKs kept for reference and go `NULL` if the product is deleted.

## Numbering

Human-facing identifiers (`orderNumber`, `quoteNumber`, `invoiceNumber`) are
generated by the admin API. The storefront should display them but not mint
them. Current prefixes: `TMH-`, `TMH-Q-`, `TMH-INV-`.

## Order fulfilment (Phase 5)

The admin app owns every `Order.status` transition:
`PAID → PROCESSING → SHIPPED → DELIVERED`, with `CANCELLED` (only before
shipping) and `REFUNDED` (any non-terminal state) as exits. Each transition
stamps its timestamp — `paidAt`, `processingAt` (added in migration
`20260902100845_order_processing_at`), `shippedAt`, `deliveredAt`,
`cancelledAt`, `refundedAt` — and appends an `audit_logs` row. The storefront
reads `status` + these timestamps + `carrier` / `trackingNumber` for its
order-tracking page and should treat them as authoritative (no webhook yet;
re-fetch on view). See `docs/API.md` → "Storefront order-tracking contract".
`internalNote` is staff-only and must never be shown to a customer.
